# Lab 2 Scenario

## 목표

이번 실습 2의 목표는 `order-service`의 주문 생성 흐름에 Outbox 패턴을 적용하고,
CDC 기반으로 Kafka 이벤트를 발행할 수 있는 최소 구조를 구현하는 것이다.

핵심은 기존 서비스를 한 번에 모두 이벤트 기반으로 바꾸는 것이 아니라,
대표 시나리오 1개를 선택해서 "주문 생성 이벤트가 안전하게 기록되고,
비동기 파이프라인으로 전달된다"는 것을 끝까지 증명하는 것이다.

이번 실습에서는 이 흐름을 `EDA(Event-Driven Architecture) MVP` 로 정의한다.
즉, 시스템 전체를 완전한 이벤트 기반으로 재작성한 것은 아니지만,
주문 생성이라는 대표 시나리오에 대해 이벤트 발행과 소비의 핵심 패턴을 적용한 상태다.

## 현재 구조의 문제

현재 `order-service`는 주문 생성 과정에서 `user-service`, `product-service`를 직접 호출하고,
주문 저장 이후의 후속 처리를 이벤트로 분리하지 않은 동기 중심 구조다.

이 구조의 한계는 다음과 같다.

- 주문 처리와 후속 작업이 강하게 결합되어 있다.
- 주문 저장과 이벤트 발행을 별도 처리하면 데이터 정합성 문제가 생길 수 있다.
- 대량 트래픽 상황에서 후속 작업이 늘어날수록 응답 지연과 장애 전파 가능성이 커진다.
- 새로운 소비자를 추가할 때 주문 서비스 코드 변경 범위가 커질 수 있다.

## 선택한 대표 시나리오

대표 시나리오는 `주문 생성`이다.

세부 흐름은 아래와 같다.

1. 클라이언트가 주문 생성 API를 호출한다.
2. `order-service`는 기존 검증과 재고 차감 로직을 수행한다.
3. 주문 엔티티를 저장한다.
4. 같은 트랜잭션 안에서 `outbox_event` 테이블에 `ORDER_CREATED` 이벤트를 저장한다.
5. Debezium Connector가 해당 row 변경을 CDC로 감지한다.
6. Kafka 토픽으로 이벤트를 발행한다.
7. Consumer는 이 이벤트를 읽어 로그를 남기거나 후속 처리의 시작점으로 사용한다.

이번 실습에서는 기존 동기 주문 로직을 바로 제거하지 않는다.
먼저 이벤트 발행의 안정성과 전체 파이프라인의 연결을 검증하는 데 집중한다.

## 기대 효과

이 시나리오를 통해 아래 효과를 기대한다.

- 주문 저장과 이벤트 기록을 같은 트랜잭션 안에서 처리하여 정합성을 높일 수 있다.
- 이벤트 발행을 DB 트랜잭션 이후의 비동기 파이프라인으로 분리할 수 있다.
- 향후 결제, 알림, 통계 같은 후속 작업을 consumer 추가만으로 확장할 수 있다.
- 실습 범위를 과도하게 넓히지 않으면서도 Outbox + CDC + Kafka의 핵심 가치를 설명할 수 있다.

## 왜 이 시나리오를 EDA라고 볼 수 있는가

이번 구현은 아래 조건을 만족하므로 EDA 구조라고 설명할 수 있다.

- 주문 서비스가 상태 변화를 이벤트로 기록한다.
- 이벤트는 Outbox 테이블에 저장되어 서비스 내부 상태 변화와 함께 관리된다.
- Debezium CDC가 이 이벤트를 감지해 Kafka로 전달한다.
- 별도 consumer가 Kafka topic을 구독하고 이벤트를 소비한다.

즉, 후속 처리가 직접 호출이 아니라 "이벤트 발행 -> 브로커 전달 -> 소비자 반응" 구조로 연결되므로,
주문 생성 시나리오 기준 EDA 패턴이 성립한다.
